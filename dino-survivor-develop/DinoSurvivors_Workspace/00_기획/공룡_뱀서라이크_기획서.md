대멸종 이후 유일하게 살아남은 공룡이, 아버지의 유언에 따라 선조들의 지혜(스킬)를 모아 강해지며 공룡시대의 재림을 도모한다. 적은 포유류. 깊은 서사 전개 없이 프롤로그 개그 컷신 정도로만 다룬다.

## 2. 코어 루프

```
이동 (플레이어 조작)
  → 자동 공격 (장착 액티브 스킬)
    → 몹 처치 → 경험치 획득
      → 레벨업 → 스킬 선택지 제시
        → 스킬 만렙(Lv5) 시 진화 + 조건 충족 시 합체
          → 웨이브 난이도 상승 (시간 경과)
            → 생존 지속 or 사망
```

몹 스폰은 **웨이브형**(시간 경과에 따라 스폰량/속도 증가)으로 확정. 생태계 시뮬레이션형(몹 AI 상호작용)은 채택하지 않음 — 개발 난이도상 프로토타입 범위 밖.

## 3. 캐릭터 시스템

### 3.1 차별화 요소
캐릭터(공룡 종족)별 차별점은 아래 두 가지로 구성:

1. **패시브** — 캐릭터 고정, 게임 내내 유지
2. **시작 스킬** — 캐릭터가 시작 시 기본 장착하는 액티브 하나. 배타적 소유가 아니라 초기 장착일 뿐이며, 공용 스킬 풀에도 동일하게 포함됨 (다른 종족도 레벨업으로 같은 스킬을 획득 가능)

### 3.2 슬롯 구조
- 액티브 슬롯: **6개** (시작 스킬 포함, 교체 가능)
- 시작 스킬은 6슬롯 중 하나를 기본으로 차지하지만, 플레이어가 원하면 다른 스킬로 교체 가능 (정체성 vs 유연성의 선택 긴장감을 의도적으로 남김)

### 3.3 스킬 풀 구조
- **공용 스킬 풀**: 전종족 공통, 시작 스킬을 포함한 모든 스킬이 이 풀 하나에 속함. 어떤 캐릭터든 랜덤으로 타종족 스킬(혹은 자신의 시작 스킬)을 획득 가능 (크로스오버)
- 종족별 배타적 전용 스킬은 없음 — "이 스킬은 특정 캐릭터만 가질 수 있다"는 규칙 자체를 두지 않음

### 3.4 프로토타입 범위
- 캐릭터 1종 (티라노사우루스)으로 시작. 패시브 시스템은 2종 이상부터 비교 대상이 생기므로 버티컬 슬라이스(M3) 단계에서 추가

## 4. 스킬 시스템

### 4.1 설계 원칙
> **"생물학적 트리거 + 즉시 과장된 결과"**
> 실제 공룡의 습성/신체 특징을 논리적 도약 없이 그 자리에서 과장한다. "생물학 → 판타지로 점차 나아가는" 방식은 뇌절처럼 느껴질 위험이 있어 채택하지 않음. 처음부터 끝까지 동일한 톤 유지.

체크리스트: *"이름+한 줄 효과를 읽고 머릿속에 구체적인 웃긴 장면이 그려지는가?"*

### 4.1.1 플레이버 텍스트 보이스 (신규 확정)
스킬 메커니즘뿐 아니라 **설명 문구 자체의 목소리**도 톤 일관성의 핵심 요소로 확정. 아래 2문장 공식을 전 스킬 설명에 기본 템플릿으로 적용:

```
1문장: 그럴듯한 실제/유사 사실을 다큐멘터리 내레이션 톤으로 진지하게 전달 ("~였다고 합니다")
2문장: 그 진지함을 스스로 깨는 짧은 자각형 애드립 (능청스러운 반문/인정)
```

**기준 예시** (산탄, 딜로포사우루스):
> "딜로포사우루스의 볏은 탄창 겸 가늠자였다고 합니다. 뭐, 그랬을 수도 있잖아요?"

이 템플릿을 8~9개 스킬 설명 전체에 일괄 적용하는 카피라이팅 작업이 별도로 필요함 (버티컬 슬라이스 단계 권장).

### 4.2 스킬 목록 (가칭, 프로토타입용 8종)

| 스킬명 | 종족 모티브 | 구분 | 태그 | 효과 초안 |
|---|---|---|---|---|
| 물기 | 티라노사우루스 | 공용 액티브 (**티라노 시작 스킬**) | `suction` | 물면 근처 몹을 끌어당겨 씹음 (좁은 물기 → 광역 흡입으로 반전) |
| 박치기 돌진 | 파키케팔로사우루스 | 공용 액티브 | `dash` | 일직선 돌진, 관통 데미지 + 넉백 |
| 골판 두르기 | 스테고사우루스 | 공용 액티브 | `orbit` | 몸 주변 회전하며 지속 데미지 |
| 철퇴 | 안킬로사우루스 | 공용 액티브 | `melee` | 느림, 강한 한방 + 강한 넉백 |
| 새끼낳기 | 마이아사우라 | 공용 액티브 | `summon` | 새끼 소환, 자동 근접 전투 (LoL 요릭 구울 참고) |
| 음파 | 파라사우롤로푸스 | 공용 액티브 | `burst` | 주기적으로 광역 충격파 발생 |
| 긴 목 | 브라키오사우루스 | 공용 **패시브** | `passive` | 아이템/경험치 수집 범위 증가 |
| 손톱 미사일 | 테리지노사우루스 | 공용 액티브 | `ranged_pierce` | 손톱이 빠져나가 일직선 관통 발사 |
| 산탄 | 딜로포사우루스 | 공용 액티브 | `ranged_spread` | 볏이 탄창처럼 부채꼴로 다수 발사. *"딜로포사우루스의 볏은 탄창 겸 가늠자였다고 합니다. 뭐, 그랬을 수도 있잖아요?"* |

**태그 체계 (4.3.1 참고)**: 표의 태그는 스킬당 하나지만, 데이터 스키마상으로는 스킬 하나가 여러 태그를 동시에 가질 수 있음 (예: 소환수가 투사체를 쏘면 `summon`+`projectile`). 지금은 변주 체크용으로 한 개씩만 부여했지만, 이후 "태그 대상 버프"(예: 소환수 강화)의 타겟팅 키로 그대로 재사용.

**변주 체크**: 근접(철퇴)·오빗(골판)·돌진(박치기)·소환(새끼)·버스트(음파)·원거리 관통(손톱)·원거리 확산(산탄)·흡입(물기)·패시브(긴목) — 겹침 없이 고르게 분산됨.

**주의**: 골판 두르기(지속형)와 음파(순간 버스트형)는 둘 다 "몸 주변 광역"이라 컨셉이 비슷해 보이지만, 지속 딜 vs 스파이크 딜로 역할을 분리해 차별화.

### 4.3 성장 & 진화 구조

```
Lv.1 ── Lv.2 ── Lv.3 ── Lv.4 ── Lv.5(만렙)
         수치↑   특징적   수치↑     │
                 강화              ① 진화 (자동 발동, 신규 형태로 대체)
                                    │
                         [합체 조건 충족 시]
                                    │
                              ② 합체 (진화 스킬 여러 개 → 궁극 스킬 하나)
```

- **레벨업 원칙**: Lv2·Lv4는 수치 증가만 (비주얼/동작 변화 없음). Lv3은 **특징적 강화** — 수치가 아니라 스킬의 동작 자체가 바뀌는 지점 (예: 물기가 Lv3부터 광역 흡입으로 반전). 스킬마다 구체 내용은 개별 설계 필요 (8장 Open Question)
- **만렙 기준**: 5레벨 (짧은 런 안에 도달 가능해야 함)
- **진화**: 스킬이 Lv5(만렙)에 도달하면 **자동으로** 새로운 "진화형" 스킬로 교체됨 (트리거 아이템 불필요 — 트리거 아이템은 4.5의 "합체"에만 사용). 각성처럼 원래 스킬 자리에서 수치만 오르는 게 아니라, 별도의 진화형 SkillData로 완전히 대체
- **진화 스킬의 레벨 규칙**: 진화형 스킬은 **만렙 = Lv1**로 판정. 즉 진화가 곧 그 계열의 최종 상태이며, 진화 후 추가 레벨업은 없음
- **합체 조건**: 합체 레시피에 등록된 재료가 **전부 진화를 마친 상태**(=각자 만렙인 Lv1 진화형)일 것. 진화 스킬의 만렙이 1이므로 실질적으로 "재료를 전부 진화시켰는가"와 동일한 조건 (클라이맥스 지향 유지. 튜닝 난이도 있음 — 4.4 참고)

#### 4.3.1 태그 시스템
- 스킬은 `SkillData.tags: Array[StringName]`로 다중 분류됨 (예: `melee`, `summon`, `projectile`, `bomb`). 4.2 표의 값은 변주 체크용으로 하나씩만 부여했지만, 스킬 하나가 여러 태그를 동시에 가질 수 있는 구조
- **용도**: (1) 신규 스킬 추가 시 기존 아키타입과 안 겹치는지 변주 체크, (2) 향후 태그를 겨냥한 버프의 타겟팅 키 (예: "소환수 강화" 효과가 `summon` 태그를 가진 스킬 전체에 적용)
- 진화/합체로 스킬이 교체될 때 태그도 새로 부여됨 — 진화형이 원본과 다른 정체성을 가지면(예: 근접형이 진화하며 광역형이 되는 경우) 태그도 그에 맞게 갈아낌
- **내부 id ↔ 노출 라벨 분리**: `tags`에 담기는 값(`summon` 등)은 시스템 내부 식별자일 뿐, 화면에는 `TagDatabase`(Autoload, `autoload/tag_database.gd`) 안의 `DISPLAY_NAMES` 딕셔너리를 거쳐 한글 라벨(`소환수` 등)로 변환되어 노출됨. 새 태그를 추가하면 이 딕셔너리에 한 줄만 추가하면 됨 (스킬 카드는 `TagDatabase.joined_display_names(tags)`로 조회)

#### 합체 재료 구조
- **재료 개수**: 기본 2개. 특정 레시피는 예외적으로 3개까지 허용 — `FusionRecipe.ingredients`가 배열이라 스키마 변경 없이 지원
- **레이어**: 단일 레이어로 통합. 과거에는 "공용 합체(풀+풀)"와 "고유 합체(고유 액티브+풀)"를 구분했지만, 3.3에서 배타적 시작 스킬 개념을 없앤 이상 그 구분은 의미가 없어져 폐지 — 재료 출처와 무관하게 레시피만 맞으면 동일하게 합체
- **결과**: 재료로 쓰인 진화 스킬 전부가 보유 목록에서 사라지고, 합체 결과 스킬 하나만 슬롯에 남음
- **레시피**: 구체 조합은 미정이나, `FusionRecipe`(재료 N개 + 결과물 1개) 리소스로 시스템은 이미 구현되어 있어야 함

**프로토타입 확정 조합**: `새끼낳기 진화형 + 음파 진화형` → (가칭) "새끼들의 대합창" — 소환형+버스트형으로 태그가 겹치지 않아 합쳐졌을 때 완전히 새로운 패턴이 나옴. 서사적으로도 마이아사우라(모성 습성)와 파라사우롤로푸스(울음소리)가 자연스럽게 연결됨.

### 4.4 밸런싱 고려사항 (재료 전부 진화 조건에 따른 리스크)
- 웨이브형 런(15~20분) 안에서 스킬 2개를 모두 진화(=만렙)까지 찍으려면 아래 장치가 사실상 필수:
  1. **가중치(피티) 시스템**: 이미 보유한 스킬이 레벨업 선택지에 더 자주 등장 (보유 스킬 2~3배 가중 권장)
  2. **슬롯 수 제한**: 6슬롯 — 슬롯이 늘어날수록 분산되어 만렙 달성이 어려워지므로 가중치를 더 세게 조정할 필요 있음
  3. **진화 타이밍 목표**: 런 후반 70~80% 지점 (웨이브 난이도 스파이크와 겹치도록 설계 — "위기 때 터지는 한 방" 연출)
  4. **주의**: 진화 스킬의 레벨 규칙(4.3, 만렙=Lv1)을 나중에 1보다 크게 바꾸면 이 리스크가 한 단계 더 누적되므로, 바꾸려면 위 장치들을 함께 더 세게 조정해야 함

### 4.5 진화·합체 트리거 방식 (확정)

- **개별 진화 (Lv5 도달 시)**: 자동 발동. 트리거 아이템 불필요 — 파트너 유무와 무관하게 만렙에 도달하는 즉시 진화형으로 교체
- **합체**: 트리거 아이템 방식 유지. 재료가 **전부 진화를 마친 상태**에서 "합체 트리거 아이템"을 보유하면 즉시 합체 발동
  - **아이템 획득 경로**: 정예 개체 처치 시 드랍 (몹 티어 시스템, 6.2 참고와 연동)
  - 레벨업 화면에 별도 선택지를 끼워넣는 방식이나 자동 발동 대신, **"강한 적을 잡아야 다음 단계로 갈 수 있다"는 행동 목표**가 생기는 쪽을 선택
  - **구현 순서**: 몹 티어/드랍테이블 인프라(G2)가 선행되어야 하므로, 실제 트리거→합체 연결 로직은 G6(합체 시스템)에서 구현

### 4.6 장기 확장 옵션 (프로토타입 범위 밖, 참고용)
- 『볼X핏』형 다단계 연쇄 합체(1차 합체 결과물이 다시 2차 합체 재료가 되는 구조) 검토 가능
- 채택 시에도 데이터 구조는 이미 "재료 리스트(N개) + 결과물"의 범용 레시피 형태(`FusionRecipe`)라 그대로 재사용 가능
- 서사 단계 네이밍 예: 선조의 지혜 → 부족의 힘 → 태초의 힘

## 5. 차별적 시스템 (게임의 시그니처)

> 뱀서류는 비슷한 토대 위에 저마다의 "킥"을 얹는 장르. 아래 3종은 "공룡 + 진화"라는 소재를 게임 시스템 층위로 끌어들여, 다른 뱀서류와 구별되는 지점을 만들기 위해 설계됨. 공통 원칙: **실시간 계산 부담을 주지 않는다** — 탄막 한복판에서 우선순위를 계산해야 하는 시스템은 장르 근본 쾌감과 충돌하므로 배제. 판단은 항상 정지 화면이나 드문 트리거에서만 발생.

### 5.1 유전 시스템

**개념**: 런이 끝날 때(사망/생존 무관) 형질 1개를 다음 런에 물려줄 수 있음. 파워가 누적되는 시스템이 아니라 **바통 터치** 구조 — 골드 기반 통합 강화가 이미 성장 축을 담당하므로, 유전은 순수하게 "정체성 로테이션" 역할만 수행.

- **선택 시점**: 런 시작 시, **기본 시작 스킬 vs 유전받은 액티브 중 택 1**
- **유전 슬롯**: 항상 1개만 유지, 누적되지 않음 (매 런 교체 가능)
- **범위**: 종족 무관 전체 공용 혈통 (티라노 런에서 얻은 형질을 스테고 런이 물려받을 수 있음 — "선조가 다른 종이었어도 지혜는 후손에게 전해진다")
- **서사적 정합성**: "유일한 생존자"인 아버지가 아니라, 그 유언을 이어받은 **후손**을 플레이어가 연기하는 구조이므로 멀티런과 스토리가 충돌하지 않음
- **장기 아이디어 (보류)**: 혈통 기록(가계도 로그) — 파워에 영향 없는 순수 수집/기록 UI. 세로로 길어지는 리소스 부담으로 지금은 아이디어로만 남김. 필요 시 재검토

### 5.2 스탠스 전환 (사족/이족 보행)

**개념**: 공룡 진화사의 실제 핵심 축(사족↔이족 보행 전환)을 게임 메커니즘으로 치환.

- **종족별 기본 자세 고정**: 예) 티라노=이족, 안킬로사우루스=사족 등 신체 구조에 맞게 배정
- **전환 트리거**: 실시간 토글이 아니라, **기믹 장소(둥지류 거점) 도달 시에만** 전환 선택 가능. 화면 정지 + 선택지 형태
- **유지**: 한 번 전환하면 해당 런이 끝날 때까지 유지 (되돌리려면 같은 유형의 기믹 장소를 다시 찾아야 함)
- **효과 차등**:

| 자세 | 이동 | 판정 | 유리한 스킬 아키타입 |
|---|---|---|---|
| 사족보행 | 빠름 | 낮은 프로필 | 근접/돌진형 |
| 이족보행 | 느림 | 넓은 판정 | 원거리/광역형 |

- 스킬별로 "사족 전용/이족 전용/공용" 태그 부여 → 자세 전환이 곧 빌드 스위칭

### 5.3 탈피 (긴급탈출)

**개념**: 전용 버튼으로 언제든 발동하는 독립 시스템. "생존기"와 "빌드 정리 도구"를 동시에 충족.

```
[긴급탈출 버튼]
  → 게임 일시정지
    → 반납할 액티브 1개 직접 선택 (시작 스킬 포함, 전부 대상)
      → 화면 전체 몹 일격 클리어 (희생 스킬 레벨에 비례한 위력)
        → 해당 슬롯 비워짐, 쿨타임 시작
```

- **반납 스킬 선택**: 플레이어 직접 지정 (정지 화면이므로 실시간 계산 부담 없음)
- **대상 범위**: 시작 스킬 포함 모든 액티브 (종족 정체성보다 전략적 자유 우선 — 5.1, 4.2 슬롯 교체 원칙과 동일한 철학)
- **남용 방지**: 쿨타임 (구체 수치는 프로토타입 실측 튜닝)
- **트레이드오프**: 진화·합체까지 키워온 스킬을 반납하면 그 투자를 그대로 잃음 (시작 스킬이라고 예외를 두지 않음 — 의도된 긴장감)
- **연출 방향**: 허물을 벗으며 터지는 이미지 (테마 정합성)

### 5.4 세 시스템의 관계

| 시스템 | 발동 시점 | 성격 |
|---|---|---|
| 유전 | 런 시작 시 1회 | 기본 액티브 vs 유전 액티브 택1 |
| 스탠스 전환 | 기믹 장소 도달 시 (드묾) | 사족/이족 재선택, 판 끝까지 유지 |
| 탈피 | 전용 버튼, 쿨타임 내 언제든 | 스킬 하나 반납 + 화면 클리어 |

세 시스템 모두 "판단은 정지 화면 또는 드문 트리거에서, 체감은 실시간으로"라는 동일한 원칙을 공유하며, 서로 다른 층위(런 간/공간/전투 진행도)에서 작동해 전략적 밀도를 만듦.

**개발 우선순위**: 5.3(탈피)은 프로토타입 범위에 포함 가능한 수준(독립 버튼 + 쿨타임 + 화면 클리어 로직). 5.1(유전), 5.2(스탠스)는 세이브 시스템/기믹 장소 등 추가 인프라가 필요해 버티컬 슬라이스(M3) 이후 권장.

## 6. 몹 & 성장 경제 시스템

### 6.1 몹 티어/단계 구조

몹은 **일반(NORMAL) / 정예(ELITE) / 보스(BOSS)** 3개 티어로 나뉘고, 각 티어 안에서 **단계(stage)**가 시간에 따라 순차적으로 강해짐 (예: 일반 몹 1단계 쥐 → 2단계 고양이).

| 티어 | 스폰 방식 | 예시 |
|---|---|---|
| 일반 | 반복 스폰, 시간 경과 시 상위 단계로 교체 | 쥐(0초~) → 고양이(90초~) |
| 정예 | 반복 스폰이지만 간격이 김 (예: 30초마다) | 4.5의 진화 트리거 아이템 드랍원 |
| 보스 | 지정 시점에 단 1회 스폰 | 180초 시점 |

### 6.2 드랍 테이블

몹 처치 시 확률 기반으로 아이템이 드랍됨. 항목마다 독립 확률(중복 드랍 가능) — 예: 경험치 100% + 골드 25%. 정예/보스는 더 높은 확률·수량의 전용 테이블을 가짐.

### 6.3 성장 경제 — 네 층위

로그라이크 문법에 따라, 성장 축을 범위(공용/개별)와 지속성(리셋/누적)으로 나눠 네 층위로 분리:

| 층위 | 범위 | 리셋 여부 | 역할 |
|---|---|---|---|
| 레벨업/스킬 (4장) | 런 내 | 매 런 리셋 | 그 판의 빌드 |
| 유전 (5.1) | 런 간, 종족 공용 | 누적 없음(교체만) | 정체성 로테이션 |
| **골드 강화** | 런 간, 종족 공용 | 영구 누적 | 범용 성장 (제너럴리스트) |
| **캐릭터 숙련도** | 런 간, 종족별 개별 | 영구 누적 | 그 종족을 깊이 판 보상 (스페셜리스트) |

#### 골드 강화 (MetaUpgrades)
- 런 종료 후 메인 화면에서 골드로 구매하는 영구 강화. **종족 공용** — 한 번 사면 모든 종족에 적용
- 비용은 레벨이 오를수록 상승하는 지수 곡선 (`cost_base × cost_growth^(레벨-1)`)
- 대상 스탯: 기초/세부 스탯 전부 (6.4 참고)

#### 캐릭터 숙련도 (CharacterMastery)
- **종족별로 개별 누적**. 그 종족으로 플레이한 만큼 그 종족만 강해짐
- **획득 방식**: 생존 시간 비례 (구체 수치 미정)
- **보너스 구성 2단**:
  - 매 레벨: **기초 스탯만** 소폭 성장 (체력/공격력/방어력 — 세부 스탯인 쿨감·치명타 등은 제외)
  - **마일스톤(N레벨마다)**: 시작 스킬/패시브를 직접 강화 (예: "물기 데미지 +15%"). 간격은 3레벨/5레벨 중 미정, 프로토타입 이후 결정

### 6.4 스탯 체계

플레이어가 가질 수 있는 스탯을 **기초(basic)**와 **세부(detail)**로 분류 (숙련도의 매 레벨 성장이 기초 스탯에만 적용되는 규칙의 근거).

| 분류 | 포함 스탯 |
|---|---|
| basic | 최대체력, 공격력 배율, 방어력 |
| detail | 이동속도, 쿨다운 배율, 수집 범위, 치명타 확률 |

**스탯 변경자(StatModifiers) 원칙**: 모든 패시브/버프 효과는 "어떤 스탯을, 어떻게, 얼마나" 바꾸는지로 구조화 (자유 텍스트 아님). 효과 출처(`source_type`): 종족 패시브, 스킬 패시브, 스탠스, 메타 강화, 숙련도. 중첩 규칙은 `additive_percent`(퍼센트 효과는 서로 합산 후 마지막에 한 번 곱함)로 통일 제안 — **팀 확정 필요** (8장 참고).

### 6.5 데이터 관리 (엑셀 연동)

위 시스템들의 실제 수치는 `공룡_뱀서라이크_기획데이터.xlsx`에서 관리. Species/Skills/FusionRecipes/Enemies/LootTables/Stats/StatModifiers/MetaUpgrades/CharacterMastery/MasteryBasicGrowth/MasteryMilestones/BalanceConfig/Legend/OpenQuestions/Changelog 15개 시트로 구성되며, 각 시트의 `id` 컬럼은 Godot `data/` 폴더의 `.tres` 파일명과 1:1 대응.

## 8. 미해결 사항 (Open Questions)

1. 합체 시 원본 스킬 소모 방식: 슬롯에서 완전히 사라지고 대체되는지, 재료가 유지되는지
2. 향후 2번째 종족 추가 시 시작 스킬을 어떻게 배정할지 (밸런스 기준점 필요 — 배타성이 없으므로 "겹쳐도 되는지"도 함께 결정)
3. 플레이버 텍스트 보이스 템플릿(4.1.1)을 나머지 스킬 8종에도 일괄 적용하는 카피라이팅 작업 필요
4. 탈피 쿨타임 수치, 최소 보유 액티브 제한(전부 반납 방지) — 프로토타입 실측 튜닝 필요
5. 스탠스 전환용 기믹 장소를 M2(프로토타입)에 일부 넣을지, M3(버티컬 슬라이스)로 완전히 미룰지
6. 숙련도 마일스톤 간격 (3레벨 vs 5레벨) — 프로토타입 이후 결정
7. 숙련도 획득 구체 수치 (분당/초당 몇 xp)
8. MetaUpgrades 비용 곡선 실제 값 (`cost_base`/`cost_growth`는 엑셀상 가안)
9. 스탯 중첩 규칙(`additive_percent` 통일) 최종 확정 — 현재는 제안 상태
10. 나머지 스킬 8종의 정확한 수치(데미지/쿨다운/범위) — `공룡_뱀서라이크_기획데이터.xlsx`의 Skills 시트에서 관리
11. 스킬별 Lv3 "특징적 강화"의 구체 내용 (스킬 9종 각각 무엇이 바뀌는지) — 미정

# 부록: Godot 프로토타입 개발 마일스톤

> 목표: "이동하고 때리는 게 재밌나 + 진화·합체가 재밌나"를 최소 비용으로 검증
> 대상: 2인 초보 팀, Godot 4.x 기준
> **팀 역량**: 메인 개발자 — 코딩 지식 있음, 게임개발 경험 없음 / 서브 개발자 — 게임 관련 지식 있음, 코딩 지식 거의 없음

## 역할 분담 원칙

Godot은 에디터 안에서 코드 없이 처리 가능한 작업(씬/노드 배치, 애니메이션, 파티클, Resource 데이터 입력, UI 레이아웃)이 많은 엔진입니다. 이 특성을 활용해 "코딩 여부"가 아니라 "코드가 필요한 작업인가"로 역할을 나누는 것을 추천합니다.

| 담당 | 역할 | 구체 작업 예시 |
|---|---|---|
| 메인 개발자 (코딩 O) | 시스템 로직 전담 | GDScript 작성: 이동, 스포너, 전투 판정, 스킬 베이스 클래스, 진화·합체 로직 |
| 서브 개발자 (게임지식 O, 코딩 X) | 콘텐츠 & 데이터 & QA | 스킬 수치를 Resource(.tres)에 입력, 웨이브 난이도 커브 값 조정, UI 레이아웃을 에디터에서 배치, 지속적 플레이테스트 및 재미 피드백, 밸런스 수치 제안 |

**핵심 팁**: 메인 개발자가 스킬/몹 데이터를 코드에 하드코딩하지 않고 처음부터 Godot의 `Resource`(커스텀 데이터 리소스)로 분리해서 설계하면, 서브 개발자가 코드를 몰라도 에디터에서 숫자만 조정하며 직접 튜닝에 참여할 수 있습니다. (예: 스킬 데미지, 쿨다운, 웨이브 스폰 간격 등을 Inspector 창에서 직접 수정)

**서브 개발자의 코딩 입문 여지**: 완전히 코드를 배제하기보다, GDScript의 가장 쉬운 부분(예: `export` 변수 조정, 간단한 `if`문 수준의 몹 AI 튜닝)부터 메인 개발자가 옆에서 짧게 알려주며 참여시키면 팀 전체의 병목이 줄어듭니다. 강제할 필요는 없지만, 여유가 되면 시도해볼 가치는 있습니다.

## 일정 버퍼: 학습 곡선 반영

두 분 다 Godot 자체가 처음이라면, 아래 마일스톤의 기간은 **학습 시간이 포함되지 않은 순수 작업 시간**입니다. 실제로는:
- **G0~G1 사이에 "Godot 공식 튜토리얼 학습 기간" 1~2주를 별도로 추가**하는 것을 강력 추천합니다 (공식 "Your first 2D game" 튜토리얼이 이번 프로젝트의 코어 루프와 구조가 상당히 비슷해서 좋은 출발점이 됩니다)
- 이후 각 마일스톤 기간에 **1.5배 정도의 버퍼**를 감안하는 게 현실적입니다 (예: G2 "4~6일" → 실질적으로 6~9일 정도로 예상)
- 총 예상 기간도 4~6주가 아니라 **6~9주 정도로 재조정**하는 게 안전합니다

## G0. 환경 세팅 ✅ 완료
- 프로젝트 구조를 콘텐츠(`data/`)와 로직(`scripts/`) 분리 방식으로 구성 — `autoload/`, `data/`, `resource_types/`, `scenes/`, `scripts/`, `assets/`
- Git 세팅, `.gitignore` 적용
- **실제 구현이 당초 계획보다 확장됨**: 스킬/종족/몹/드랍테이블을 전부 Resource 스키마(`resource_types/*.gd`)로 정의해, 새 콘텐츠 추가 시 코드 수정 없이 `.tres` 파일만 늘리면 되는 구조로 완성
