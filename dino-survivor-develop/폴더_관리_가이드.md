# 프로젝트 폴더 관리 가이드 (초보 2인 팀용)

## 1. 최상위 작업공간 — Godot 프로젝트 "밖"부터 정리하기

지금 Godot 프로젝트(`DinoSurvivorsPrototype/`)와 기획서(`.md`)가 서로 다른 곳에 흩어져 있을 텐데, 컴퓨터(또는 공유 드라이브)에 아래처럼 상위 폴더 하나를 만들어서 그 안에 전부 묶어두는 걸 추천합니다.

```
DinoSurvivors/                        ← 최상위 작업 폴더
├── 00_기획/                          ← 문서, 회의록, 레퍼런스 (Godot 프로젝트 밖)
│   ├── 공룡_뱀서라이크_기획서.md
│   └── 레퍼런스이미지/
├── 01_게임프로젝트/
│   └── DinoSurvivorsPrototype/        ← project.godot이 있는 실제 Godot 프로젝트
├── 02_원본에셋/                       ← Godot에 넣기 전 원본 (psd, aseprite, wav 마스터 등)
│   ├── art/
│   └── audio/
└── 03_빌드/                          ← 내보내기(export)한 실행 파일
```

**왜 이렇게 나누는가**: Git으로 버전관리할 대상은 `01_게임프로젝트/` 뿐이어야 합니다. 기획 문서는 Google Docs나 Notion처럼 따로 관리해도 되고, 원본 에셋(레이어 있는 psd 파일 등)은 용량이 커서 Git에 안 어울리니 Drive 같은 곳에 따로 보관하는 게 낫습니다. Godot 프로젝트 폴더 안에는 **"이미 완성돼서 게임에 실제로 쓰이는 최종 파일"만** 있어야 한다는 원칙만 기억하면 됩니다.

## 2. Godot 프로젝트 내부 — "언제 새 폴더를 만들지" 감 잡기

지금 짜드린 구조(`autoload/`, `data/`, `resource_types/`, `scenes/`, `scripts/`, `assets/`)를 기준으로, 앞으로 파일이 늘어날 때 아래 규칙만 따르면 안 흔들립니다.

| 규칙 | 설명 |
|---|---|
| **콘텐츠 vs 로직 분리** | "숫자/텍스트만 다른 것"은 `data/`에 (스킬, 종족, 웨이브 등), "동작 자체가 다른 것"은 `scripts/`에. 헷갈리면 "서브 개발자가 코드 없이 고칠 수 있어야 하는가?"로 판단 — 그렇다면 `data/` |
| **폴더당 15~20개 넘으면 하위 분류** | 예: `data/skills/`에 20개 넘게 쌓이면 `data/skills/melee/`, `data/skills/ranged/`처럼 아키타입별로 쪼개기 |
| **역할이 다르면 폴더도 다르다** | 씬(`scenes/`) / 스크립트(`scripts/`) / 데이터(`data/`) / 데이터의 틀(`resource_types/`)을 절대 안 섞기 — 이미 적용된 원칙 |
| **실험용은 격리** | 테스트해보는 중인 파일은 `scripts/debug/`, `scenes/_sandbox/`처럼 이름에 표시된 폴더에만 두고, 완성되면 정식 폴더로 옮기거나(또는 대체되면 삭제하기) — 예: 임시 배경이었던 `grid_background.gd`는 청크 기반 타일맵(`scripts/world/`)이 들어오면서 삭제됨 |
| **이름 규칙 통일** | 스크립트(`.gd`)는 `snake_case` (`player.gd`), 씬(`.tscn`)은 `PascalCase` (`Player.tscn`) — Godot 커뮤니티에서 흔히 쓰는 관례. 지금 프로젝트도 이미 이렇게 되어 있으니 계속 유지 |
| **빈 폴더엔 `.gitkeep`** | Git은 빈 폴더를 추적 안 함. 나중에 채울 폴더를 미리 만들어뒀다면 그 안에 빈 파일 `.gitkeep`을 하나 넣어둬야 Git에 폴더 자체가 유지됩니다 (이미 `scenes/ui/`, `data/waves/` 등에 적용해뒀습니다) |

**이 구조의 핵심 효과**: 스킬이 9개에서 30개, 종족이 1개에서 5개로 늘어나도 `scripts/`, `resource_types/` 폴더 안의 파일 개수는 거의 안 늘어납니다. 늘어나는 건 오직 `data/` 폴더 안의 `.tres` 파일 개수뿐이에요. "프로젝트가 커질수록 관리가 어려워지는" 느낌을 최대한 늦게 받도록 짜둔 구조입니다.

## 3. 파일을 옮길 때 반드시 지킬 것

Godot 프로젝트에서 초보자가 제일 많이 겪는 사고입니다.

> **파인더(Mac)나 탐색기(Windows)에서 직접 파일을 드래그해서 옮기지 마세요.**

씬(`.tscn`)이나 프로젝트 설정 파일은 내부에 다른 파일의 **경로가 텍스트로 박혀 있습니다** (`res://scripts/player.gd` 같은 식으로). OS 파일탐색기에서 옮기면 이 경로가 자동으로 안 바뀌어서 "파일이 없다"는 에러가 납니다. 오늘 리소스 스키마 만들면서 스크립트 위치를 옮긴 것도 이 문제라, 씬 파일들 안의 경로를 일일이 손으로 고쳐야 했어요.

**대신**: Godot을 실행한 상태에서, 왼쪽 하단 **FileSystem 패널** 안에서 드래그 앤 드롭으로 옮기세요. 에디터가 알아서 참조 경로를 다 갱신해줍니다.

## 4. Git 운용 (2인 팀 기준, 가볍게)

- **브랜치**: 처음부터 복잡하게 갈 필요 없습니다. 서로 다른 파일을 작업한다면 둘 다 `main`에 바로 커밋해도 충돌이 거의 안 납니다. 같은 파일(예: `player.gd`)을 동시에 건드릴 예정이면, 미리 "지금 이거 건드릴게" 한마디만 하는 습관으로 충분합니다.
- **커밋 메시지에 태그 붙이기**: `[G2] 몹 스포너 타이머 로직 추가`, `[data] 스킬: 산탄 추가`처럼 마일스톤 단계나 폴더 이름을 앞에 붙이면, 나중에 커밋 로그만 봐도 뭐가 언제 바뀌었는지 한눈에 파악됩니다.
- **커밋은 작게, 자주**: 기능 하나가 끝날 때마다 커밋하세요. "오늘 작업한 거 한꺼번에 커밋"보다 훨씬 안전합니다 — 문제가 생겼을 때 어느 커밋에서 꼬였는지 찾기 쉬워집니다.
- `.gitignore`에 이미 Godot 캐시 파일(`.godot/` 등)이 제외되어 있으니 그대로 유지하면 됩니다.

## 5. 지금 이 프로젝트에 실제로 적용된 예시

- `data/skills/bite.tres` — "물기" 스킬 데이터. 이 파일 하나가 스킬 하나를 통째로 정의합니다. 서브 개발자가 이 파일을 Godot에서 열면(Inspector 창) 데미지, 쿨다운 등을 코드 없이 바로 조정 가능
- `data/species/trex.tres` — 티라노 종족 데이터. 위 `bite.tres`를 "시작 스킬"로 참조하고 있음 (파일끼리 서로 연결되는 방식). 시작 스킬도 공용 스킬 풀에 그대로 포함되므로, 배타적으로 소유하는 게 아니라 초기 장착일 뿐입니다
- 새 스킬을 추가하고 싶다면: `resource_types/skill_data.gd`를 열 필요 없이, `data/skills/` 안에 `.tres` 파일 하나만 더 만들면 끝

이 패턴이 앞으로 스킬 9종 → 수십 종, 종족 1종 → 여러 종으로 늘어날 때도 그대로 반복됩니다.
